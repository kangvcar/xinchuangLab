# Linux AI 陪练实训学习报告设计

## 背景

当前平台已经打通了学生实验会话、openEuler 终端、步骤进度、终端日志、AI 陪练记录和 HTML 报告生成链路。现有报告主要按时间列出终端日志和 AI 讲解，能够证明“系统记录了过程”，但还没有把数据组织成教师可评价、学生可复盘的学习证据。

本次重新设计报告生成能力，采用“学习画像型报告”为主体，并吸收正式封面和教师签章区。报告应同时服务学生和教师：学生能看到自己完成了哪些目标、哪里需要巩固；教师能快速判断完成度、操作证据、错误表现和评价建议。

## 设计目标

1. 报告呈现从流水账升级为“目标-步骤-证据-反馈-评价”的闭环。
2. 报告正文保持内容丰富但可读，附录保留完整日志和 AI 记录。
3. 第一版继续生成 HTML 和 Markdown，不强依赖 PDF。
4. 数据尽量来自现有表和实验配置，避免为第一版引入复杂新表。
5. 报告样式适合浏览器查看、课堂归档和后续打印导出。

## 使用场景

### 学生复盘

学生完成实验后生成报告，查看实验目标、步骤完成情况、关键命令证据、AI 反馈摘要和后续学习建议。报告帮助学生理解自己不是“敲过命令”，而是完成了具体 Linux 能力点。

### 教师评价

教师查看报告时，应能先通过概览判断整体情况，再进入步骤记录和关键证据确认学生真实操作过程。教师评价区保留评分、等级、评语和签名位置，方便打印或归档。

## 报告结构

### 1. 封面

封面体现正式归档感，展示：

- 报告标题：《Linux AI 陪练实训学习报告》
- 平台名称：信创 Linux AI 实时陪练实训平台
- 实验名称
- 学生编号
- 系统环境，如 openEuler
- 实验时间范围
- 实验状态
- 报告生成时间

封面样式应简洁正式，突出信创 Linux、openEuler、AI 实时陪练和容器化实训，不使用过度装饰。

### 2. 学习概览

学习概览是报告入口，面向教师快速判断和学生整体复盘。建议包含：

- 实验目标
- 步骤完成率，例如 `4 / 6`
- 已完成步骤数、未完成步骤数
- 执行命令数量
- 错误命令数量
- AI 陪练次数
- 实验用时
- 整体学习结论

整体学习结论第一版使用规则生成：

- 全部步骤 confirmed 或 completed：实验目标基本达成。
- 完成率大于等于 70%：主要流程已完成，仍有个别步骤需要巩固。
- 完成率低于 70%：建议重新完成未通过步骤并复盘关键命令。

### 3. 步骤完成记录

按实验配置中的 `steps` 顺序生成步骤表格。每行包含：

- 步骤编号
- 步骤标题
- 学习目标，优先使用 `goal`，缺失时使用 `success_criteria` 或 `hint`
- 完成状态，映射 `confirmed`、`completed`、`pending`、`locked`
- 完成时间，优先使用 `confirmed_at`，其次使用 `detected_at`
- 推荐命令，来自 `try_commands`
- 成功提示，来自 `success_hint`

状态文案：

- `confirmed`：已确认完成
- `completed`：已检测完成
- `pending`：进行中
- `locked`：未开始

### 4. 关键操作证据

正文不直接堆叠全部终端日志，而是提炼关键命令证据。每条证据包含：

- 命令
- 输出摘要
- 是否错误
- 关联步骤
- 教学意义

第一版证据提取规则：

- 优先从 `ai_coach_record.command_context` 中解析 `命令：`、`是否错误：`、`当前步骤：` 和 `命令输出：`。
- 如果 AI 记录不足，再从 `terminal_log.clean_content` 中提取可读命令片段。
- 输出摘要限制长度，保留关键结果，避免长日志破坏正文阅读。
- 错误命令单独加醒目标识，便于教师观察排错过程。

关联步骤规则：

- 如果 `command_context` 包含当前步骤，直接关联该步骤。
- 否则按命令与步骤 `try_commands`、`verification.checks`、`keywords` 的匹配关系推断。
- 无法关联时显示“未关联到具体步骤”。

### 5. AI 陪练摘要

报告正文展示 AI 陪练的关键反馈摘要，而不是完整贴满所有讲解。每条摘要包含：

- 时间
- 关联命令
- 反馈类型：成功引导、错误纠正、下一步建议、知识解释
- 摘要内容

第一版摘要可以用规则截断和分类：

- `command_context` 或 `ai_response` 含错误关键词时归为错误纠正。
- 步骤验证通过时归为成功引导。
- 其他记录归为知识解释或下一步建议。
- 摘要保留前 120 到 180 个中文字符，完整内容放入附录。

### 6. 学习表现分析

这一部分体现报告价值。第一版不必调用额外 AI，使用规则生成：

#### 掌握较好的内容

从已完成步骤中提取能力点：

- 使用步骤标题和 `goal` 生成表述。
- 示例：已完成“查看当前目录”，说明学生能够使用 `pwd` 识别当前工作目录。

#### 需要巩固的内容

从未完成步骤和错误命令中提取：

- 未完成步骤对应的目标。
- 常见错误类型对应的建议。
- 如果错误数较高，建议先复习路径、命令拼写、文件状态检查。

#### 典型错误

根据命令输出分类：

- `command not found`：命令拼写或命令不存在。
- `No such file or directory`：路径或文件不存在。
- `Permission denied`：权限不足。
- 其他含 `error`、`failed`、`cannot` 的输出归为一般执行错误。

#### 后续学习建议

结合未完成步骤和错误类型生成 2 到 4 条建议。建议要具体、可执行，例如：

- 重新练习 `pwd`、`ls -l`、`mkdir` 的组合使用。
- 每次文件操作后用 `ls -l` 验证结果。
- 遇到报错时先读错误关键词，再检查路径和文件名。

### 7. 教师评价区

教师评价区吸收正式报告的签章感，包含：

- 完成度建议
- 操作规范性建议
- 排错能力建议
- 综合评分空格
- 等级空格
- 教师评语空白区
- 教师签名
- 日期

评分建议第一版仅给参考，不自动替代教师评价。参考逻辑：

- 完成率 90% 以上：建议优秀或良好。
- 完成率 70% 到 89%：建议良好或合格。
- 完成率低于 70%：建议继续练习后再评价。
- 错误命令较多时，提示教师关注排错过程而不是只看完成率。

### 8. 附录

附录保留完整过程证据：

- 完整终端记录
- 完整 AI 陪练记录
- 技术信息：会话 ID、实验 ID、运行模式、容器名称、镜像名称、报告 ID

附录默认放在报告末尾，不干扰正文阅读。

## 数据来源

报告生成服务使用现有数据：

- `lab_session`：学生、实验、系统、容器、时间、状态。
- `experiment.task_config`：实验目标、步骤、命令建议、验证规则。
- `step_progress`：每一步状态、检测时间、确认时间。
- `terminal_log`：清洗后的终端记录。
- `ai_coach_record`：命令上下文和 AI 讲解。
- `lab_report`：报告索引和文件路径。

为支持步骤完成记录，需要 `ReportService` 从数据库读取 `step_progress`。当前已有 `Database.get_step_progress(session_id)`，不需要新增表。

## 后端设计

`ReportService.generate(session_id)` 保持作为入口，但内部拆成两层：

1. `build_report_model(session_id)`：整理结构化报告数据。
2. `render_markdown(model)` 和 `render_html(model)`：生成 Markdown 与 HTML。

建议的报告模型字段：

- `meta`
- `overview`
- `steps`
- `evidence_items`
- `ai_summaries`
- `learning_analysis`
- `teacher_evaluation`
- `appendix`

这样后续支持 PDF、模板切换或教师端预览时，可以复用同一份报告模型。

## 前端设计

第一版前端交互保持简单：

- 学生端仍通过“生成报告”按钮调用现有接口。
- 生成成功后打开 HTML 报告。
- 按钮可保留当前图标样式，避免改动主工作台布局。

后续可增强：

- 生成中显示明确状态。
- 生成失败显示错误提示。
- 教师端增加“查看报告”入口。

## 错误处理

报告生成应容忍数据不完整：

- 没有步骤进度时，步骤状态按实验配置显示为未开始。
- 没有终端日志时，正文提示暂无终端记录。
- 没有 AI 记录时，AI 摘要和附录提示暂无 AI 陪练记录。
- 会话不存在时维持当前 404 行为。
- 字段缺失时使用空字符串或“未记录”，避免生成失败。

## 样式原则

- HTML 报告使用单文件内联 CSS，便于静态访问和归档。
- 版式采用正式报告风格：封面、摘要卡片、表格、证据块、附录。
- 主色不依赖单一蓝紫渐变，使用中性底色搭配少量信创/教学感强调色。
- 表格和证据块要适合打印，避免深色大面积背景。
- 长命令和输出使用等宽字体并自动换行。

## 测试计划

后端测试新增或更新：

1. 报告模型能正确统计步骤完成率、命令数、错误数和 AI 次数。
2. 步骤进度能按实验配置顺序渲染。
3. 无日志、无 AI 记录时仍能生成报告。
4. 错误命令能被归类为典型错误。
5. Markdown 和 HTML 文件均写入报告目录，并保存 `lab_report` 索引。
6. HTML 对用户输入、命令输出和 AI 文本进行转义，避免破坏页面。

手工验证：

1. 完成一次文件管理实验后生成报告。
2. 检查概览、步骤表、关键证据、AI 摘要、教师评价区和附录。
3. 浏览器打开报告，确认版式正式、内容不溢出、中文显示正常。

## 非目标

第一版不实现：

- PDF 导出。
- 教师在线填写评语并回写数据库。
- 基于大模型重新生成整篇报告分析。
- 班级维度统计报表。
- 多模板选择器。

这些能力可以在报告模型稳定后继续扩展。
